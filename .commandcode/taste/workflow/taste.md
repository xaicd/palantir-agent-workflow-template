# Workflow preferences

- Wants work committed and pushed to BOTH remotes (origin/GitHub + gitee) — "提交推送", "push all", "git commit push" recur constantly. Confidence: 0.9
- Wants rebuild + redeploy to the shared test environment after each batch of code changes; iterates in a continuous build→deploy loop ("rebuild and redeploy", "代码更新了，继续部署"). Confidence: 0.85
- Insists the test environment always reflect the latest HEAD ("you need keep the latest version"). Confidence: 0.8
- Wants test-env/ops/admin/merchant account credentials emitted as a durable log or file, reusable for production ("你得有个日志或者文件生成", "后续生产也一样"). Confidence: 0.8
- Prefers E2E verification run against the actual deployed test environment, not just locally ("why not test env"). Confidence: 0.8
- Wants business/E2E test data created by E2E runs and cleanable afterward, while system-init data is shared. Confidence: 0.75
- Expects screenshot/visual evidence to prove UI changes, and wants the agent to capture the screenshots itself rather than asking ("APP 端 C 端 你自己截图啊", "改吧，截图为证"). Confidence: 0.75
- Prefers validating features by running them through the real UI flow (E2E on the admin console, e.g. 运营后台新增版本) instead of poking the database directly ("其实 还不如 运行一个 E2E 运营后台 新增版本 功能 验证呢"). Confidence: 0.75
- Treats documentation as a first-class deliverable: environment anchors (dev vs test URLs/IPs) and operational facts must be recorded in docs so they aren't forgotten, and when a mistake is discovered ALL related docs must be fixed, not just the code ("相关文档 要记录下来，别每次老忘记", "相关文档 都得 修复啊"). Confidence: 0.85
- Expects the full mobile release chain, not just a server deploy: build the Android APK → upload to COS → publish an app version record so installed client apps trigger the upgrade ("同时打个APP 安卓包吧，上传 COS，发个版本", "得 调用 appversion 版本接口升级吧"). Confidence: 0.7
- Deploy SOP requires a rollback point: before flipping the `latest` tag, tag the current image with a timestamped `rollback-pre-...` name, and include the exact one-command rollback in the completion report. Confidence: 0.7
- Post-deploy verification is expected end-to-end: check `/api/health/ready` (decrypt its encrypted payload to confirm real `ready` + DB/Redis storage status), confirm key routes return 200, and grep the rendered HTML for markers from the new commits. Confidence: 0.7
- Rebuild+redeploy should only be triggered by runtime code changes (`src/`, app code, `prisma/`); changes to docs/`CLAUDE.md`/`.claude/commands` don't enter the runtime image and shouldn't force a rebuild. Changes confined to static frontend artifacts go through the separate static-artifact chain (build locally → tar to static web release dir → switch nginx root/alias → reload → keep old release for rollback) and never rebuild/restart the backend image. Confidence: 0.75
- Expects the agent to derive the deploy scope itself from the code diff: when told "代码更新了，你看看变动内容决定部署内容", inspect the changed files, classify them by deploy surface, decide (and state) what will ship and what won't — rather than asking the user what to deploy. Confidence: 0.65
- Runs multiple agents with divided roles: one agent does the code development, another is reserved for build/deploy only — the deploy agent should wait for the code to land (a bare "部署一下 cend-pc" is the whole signal) and pick the right chain rather than editing code itself. Confidence: 0.7
- Public-facing verification must be run FROM the test server, not the local dev machine: the local network intercepts the production domain (redirects to a `dnspod.qcloud.com/static/webblock.html` block page, curl returns `000` / connection reset). A local failure is not evidence of a server problem — confirm DNS/TLS via `openssl s_client` and confirm the live release via `ssh ... curl` on the host. Confidence: 0.7
- Runs agents concurrently on the same repo and periodically asks for a diff/review of what the other sessions pushed ("看看变化"); expects a review that flags risky changes (schema change without a migration, dead code / commit-message-vs-code mismatch, untracked deploy files) ranked by priority. Confidence: 0.55
- For sensitive/destructive or shared-impact operations (rotating leaked secrets, rewriting shared git history, force-pushing shared remotes), prefers the agent to only report the incident and hand over a self-handling checklist rather than modify the repo or perform the operation itself. Confidence: 0.55
- When adopting a third-party tool/skill, wants it "made our own": distilled into a project-local skill under `.agents/skills/<name>/` (own SKILL.md recording the trade-offs we care about) plus a constrained local entry script — not consumed as-is, and not vendored wholesale from upstream ("搞成自己的吧", consistent with prior find-skills / hyperframes adoptions). Confidence: 0.7
- Adopted skills must be wired into the existing project machinery, not left standalone: registered in the AGENTS.md skill index, mirrored into the Hermes skills dir (`~/.hermes/skills/<project-name>/`), committed + pushed to both remotes, and the cross-session memory file updated. Confidence: 0.65
- Prefers to audit a third-party skill's real upstream SKILL.md / docs before adopting, and to pull upstream "consumer" skills only on demand — never blind-install or scatter third-party skills into global agent directories. Confidence: 0.6
- Applies the same supply-chain hygiene to tool installers: download and read the install script (or fetch the equivalent readable source) BEFORE executing it — never blind `curl ... | bash`. Confidence: 0.6
- Extends existing agents/roles rather than inventing new ones: a new capability should land as a "skill" usable by the existing digital employees / coding agents, keeping the role set and account matrix unchanged ("不加新角色，只加技能", "角色本体保持不变"). Confidence: 0.7
- When an approach is rejected mid-flight, expects the added pieces to be fully rolled back and the rollback verified by grep-ing for residual references to the removed concept. Confidence: 0.55
